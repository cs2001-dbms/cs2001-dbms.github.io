Indexing and Hashing

Why Do We Need Indexes?

Imagine a library with a million books stored in no particular order. Finding a specific title means scanning every shelf — that is linear search, and it is painfully slow for large collections.

A database index solves exactly this problem. It is a separate, smaller data structure that maps search-key values to the actual records in the main table. Think of it like the index at the back of a textbook: you look up a keyword, get the page number, and jump straight there — no full scan needed.

💡 Key insight: An index file is typically much smaller than the main data file, so searching the index is fast, and then the pointer takes you directly to the right record.

The attribute (or set of attributes) you build the index on is called the search key. An index entry looks like this:

search-key pointer
“Physics” → record #5

There are two broad families of indexes:

  • Ordered indices — entries are sorted on the search key (like an alphabetical index)
  • Hash indices — entries are scattered into buckets by a hash function (faster for exact lookups, but can’t handle range queries well)

This lecture focuses on ordered indices.

How Do We Judge an Index?

Not all indexes are equally useful. We evaluate them on four metrics:

Metric What it asks
Access types Can it handle point lookups and range queries efficiently?
Access time How fast can we find a record?
Insertion/Deletion time How much overhead does updating the index add?
Space overhead How much extra storage does the index consume?

A good index strikes the right balance — fast lookups without ballooning storage or making every insert a nightmare.

Ordered Indices

In an ordered index, entries are sorted on the search key value — exactly like an author catalog in a library. Two important variants:

  • Primary index (clustering index): The index whose search key matches the physical order of the data file itself. If your Employee table is stored sorted by emp_id, then an index on emp_id is the primary index. Sequential scans using this index are very efficient because records physically adjacent on disk are also logically adjacent.

  • Secondary index (non-clustering index): An index on a different attribute — say, salary — while the file is still physically ordered by emp_id. The salary values in the index point all over the disk, so a sequential scan through this index is much more expensive (each lookup may fetch a fresh disk block).

⚠️ A table can have only one primary index (since the data has only one physical order) but many secondary indices.

An index-sequential file is the combination: a sequentially ordered file together with its primary index. This is sometimes called ISAM (Indexed Sequential Access Method).

Dense vs. Sparse Indexes

Dense Index

A dense index has one index entry for every record in the data file.

Think of it as a full directory: every employee gets a line in the lookup table.

Index entry for emp_id = 101  →  record 1
Index entry for emp_id = 102  →  record 2
Index entry for emp_id = 103  →  record 3
...

Advantage: You can tell immediately from the index whether a record exists — no need to visit the data file at all for existence checks.

Disadvantage: The index can grow quite large.

Sparse Index

A sparse index has index entries for only some search-key values — typically one per disk block (or one per group of records).

Index entry for emp_id = 101  →  block 0  (covers records 101–200)
Index entry for emp_id = 201  →  block 1  (covers records 201–300)
...

To find a record with key \(K\): 1. Find the largest index entry with key \(< K\). 2. Follow its pointer to the data block. 3. Scan sequentially within that block until you find \(K\).

Advantage: Much smaller index — fewer entries to store and maintain.

Disadvantage: Slightly slower lookup since you have to scan within a block.

💡 Sweet spot: A sparse index with one entry per disk block is the standard recommended trade-off — small enough to fit in memory, yet granular enough to eliminate most of the sequential scan.

Primary and Secondary Indices: The Trade-Off

Primary (Clustering) Secondary (Non-Clustering)
Data order Matches the index Different from the index
Sequential scan Very efficient Expensive — random I/O
Can be sparse? Yes No — must be dense
Number per table One Many

Why must secondary indices be dense? Because records of a given secondary key value are scattered throughout the file. A sparse index would miss records that don’t happen to be at a block boundary.

⚠️ Updating indices adds overhead. Every insert, delete, or update to the table requires updating every index built on it. More indexes → faster reads, slower writes.

Multilevel Index

Here’s a practical problem: what if the primary index itself is too large to fit in main memory? Searching it becomes expensive again.

The solution is to layer another sparse index on top:

  • Inner index — the original primary index (on disk)
  • Outer index — a sparse index built on the inner index (small enough for memory)

Lookup: search the outer index (in memory) → jump to the right block of the inner index → follow the pointer to the actual data.

If even the outer index is too large, add yet another level. This idea of layering sparse indexes is exactly where B-trees come from — which we will cover in the next section.

⚠️ Indices at all levels must be updated whenever the data file changes.

Index Updates in Practice

On Deletion

  • If the deleted record was the only one with that search-key value, remove the entry from the index.
  • Dense index: treat it like any sorted-list deletion.
  • Sparse index: if the deleted record was the anchor for a block, replace its index entry with the next search-key value in that block. If the next value already has its own entry, just remove the current entry.

On Insertion

  • Dense index: look up the key; if absent, insert a new entry in sorted order.
  • Sparse index: no change needed unless a new disk block is created. If a new block is created, insert an entry for the first key in that new block.

Multilevel insertion and deletion work the same way, recursively applied to each level.

Balanced Binary Search Trees: A Recap

Before we can understand the tree structures databases use internally, it helps to revisit the classic Binary Search Tree (BST) and why “balance” matters so much.

Search Complexity Depends on Height

In a BST with \(n\) nodes, search costs \(O(h)\) where \(h\) is the tree’s height.

  • Best case (balanced): \(h \sim O(\log n)\) — perfect, this is what we want.
  • Worst case (skewed): \(h = n - 1\) — this happens when keys are inserted in sorted order. The tree degenerates into a linked list, and search becomes \(O(n)\).
Sorted insertion: 1, 2, 3, 4, 5
Resulting "tree":
  1
   \
    2
     \
      3  ← just a linked list, O(n) search

Keeping It Balanced

A BST is balanced if \(h \sim O(\log n)\). This can be guaranteed by:

  • AVL Tree: After every insert, check if any node’s left and right subtree heights differ by more than 1. If so, perform a rotation to restore balance. Named after inventors Adelson-Velsky and Landis.
  • Randomized BST: Insert keys in a uniformly random order — on average, the tree stays balanced without explicit rebalancing.
  • Skip List: A probabilistic layered structure of sorted linked lists, effectively giving \(O(\log n)\) expected performance.
  • Splay Tree: A self-adjusting BST that moves recently accessed elements to the root, giving good amortized performance for repeated lookups.

All of these achieve \(O(\log n)\) for search, insert, and delete. But they share a critical limitation:

⚠️ Balanced BSTs work brilliantly in memory but do not scale to external storage (disk). Each node access is a separate disk read, and with \(O(\log n)\) levels, that’s \(O(\log n)\) disk reads — each taking 5–10 milliseconds. For a million records, that’s painfully slow.

This is why databases need a different kind of tree.

The 2-3-4 Tree: Motivation

The problem with BSTs on disk is that each node holds only one key and has only two children. The tree must be very tall (\(O(\log n)\) levels) to hold \(n\) records.

What if we could make each node fatter — storing multiple keys and having multiple children? Then the tree would be much shorter, and we’d need far fewer disk reads to reach any record.

This idea leads to the 2-3-4 Tree (and ultimately to B-trees, the actual structure used in most database engines).

What Is a 2-3-4 Tree?

A 2-3-4 Tree is a balanced search tree where every node can hold 1, 2, or 3 keys (and correspondingly have 2, 3, or 4 children). That is where the name comes from.

The three node types:

Node type Keys stored Children Search key rule
2-node 1 (call it S) 2 left child < S; right child > S
3-node 2 (S and L) 3 left < S; middle: S–L; right > L
4-node 3 (S, M, L) 4 left < S; second: S–M; third: M–L; right > L

A leaf node can hold 1, 2, or 3 data items.

Key properties: - All leaves sit at the same depth — the tree is always perfectly height-balanced. - \(h \sim O(\log n)\), so search, insert, and delete all cost \(O(\log n)\). - Data is always kept in sorted order. - The structure generalizes to larger nodes — the B-tree is exactly this idea extended to nodes with hundreds of children.

Search in a 2-3-4 Tree

Search is a straightforward extension of BST search. At each node, compare the target key against the node’s keys and follow the appropriate child pointer. Repeat until you reach a leaf or find the key.

💡 Because all leaves are at the same depth, every search takes exactly \(O(h) = O(\log n)\) steps — no worst-case skew possible.

Insertion in a 2-3-4 Tree

Insertion always happens at a leaf. The process:

  1. Search for the expected location (the leaf where the key would go).
  2. If the leaf is a 2-node, expand it to a 3-node and insert. Done.
  3. If the leaf is a 3-node, expand it to a 4-node and insert. Done.
  4. If the leaf is a 4-node, we can’t add another key — we must split it first.

Node Splitting

Splitting a 4-node takes its middle key (M) and pushes it up to the parent. The original 4-node becomes two 2-nodes (one holding S, one holding L), both children of the parent which now absorbs M.

There are three cases depending on the parent:

Case 1 — Parent is the root (a 4-node):

    [S  M  L]          [M]
   /  |  |  \    →    /   \
  a   b  c   d      [S]   [L]
                   / \   / \
                  a   b c   d

The tree grows one level taller.

Case 2 — Parent is a 2-node:

The middle key M is absorbed into the parent, converting it from a 2-node to a 3-node. The split 4-node’s two halves (S and L) become two separate children.

Case 3 — Parent is a 3-node:

Same idea — M is absorbed, converting the parent from a 3-node to a 4-node.

Early vs. Late Splitting

There are two strategies for when to split:

  • Early splitting: Split any 4-node you encounter on the way down during a search, before you actually need to. This ensures you never have a full node at the insertion point. At most one split per level.
  • Late splitting: Only split when you actually need to insert into a 4-node. May cascade up \(O(h)\) splits in the worst case.

Both strategies produce valid trees with the same complexity \(O(h)\), but they produce different final shapes. The slides follow the early splitting strategy.

Insertion Example: Step by Step

Inserting the sequence 10, 30, 60, 20, 50, 40, 70, 80, 15, 90, 100 using the early splitting strategy.

After inserting 10, 30, 60 — all three fit into one leaf (a 4-node):

[10  30  60]

Insert 20 — the root is a 4-node, so we split it before descending. Middle key 30 becomes the new root; 10 and 60 become separate children. Then 20 is inserted into the left child:

        [30]
       /    \
  [10, 20]  [60]

Insert 50 — 50 > 30, go right. [60] is a 2-node, so just expand it:

        [30]
       /    \
  [10, 20]  [50, 60]

Insert 40 — 40 > 30, go right. [50, 60] is a 3-node, expand to 4-node and insert:

        [30]
       /    \
  [10, 20]  [40, 50, 60]

Insert 70 — root [30] is fine. 70 > 30, descend right. [40, 50, 60] is a 4-node — split it immediately (early strategy). Middle key 50 rises to join the root:

           [30, 50]
          /   |    \
   [10,20]  [40]  [60]

Now insert 70 into the right child [60]:

           [30, 50]
          /   |    \
   [10,20]  [40]  [60, 70]

Insert 80 — 80 > 50, go to right child [60, 70]. It’s a 3-node, expand it:

           [30, 50]
          /   |    \
   [10,20]  [40]  [60, 70, 80]

Insert 15 — 15 < 30, go left. [10, 20] is a 3-node, expand it:

              [30, 50]
             /   |    \
  [10, 15, 20]  [40]  [60, 70, 80]

Insert 90 — root [30, 50] is fine. 90 > 50, descend right. [60, 70, 80] is a 4-node — split it. Middle key 70 rises to join the root:

                [30, 50, 70]
               /   |    |   \
  [10,15,20]  [40] [60] [80]

Now insert 90 into the rightmost child [80]:

                [30, 50, 70]
               /   |    |   \
  [10,15,20]  [40] [60] [80, 90]

Insert 100 — root [30, 50, 70] is a 4-node — split it first. Middle key 50 becomes the new root; 30 and 70 become children:

                      [50]
                     /    \
                  [30]    [70]
                 /    \   /   \
          [10,15,20] [40] [60] [80,90]

Now insert 100. 100 > 50 → go right to [70]. 100 > 70 → go to right child [80, 90]. It’s a 3-node, expand it:

                      [50]
                     /    \
                  [30]    [70]
                 /    \   /   \
          [10,15,20] [40] [60] [80, 90, 100]

Final tree after all 11 insertions:

                         [50]
                        /    \
                     [30]    [70]
                    /    \   /   \
             [10,15,20] [40][60] [80,90,100]

Height = 2. All 11 keys stored, all leaves at the same level. A plain BST with this input could have ended up with height 10 — the 2-3-4 tree keeps it to 2.

Deletion in a 2-3-4 Tree

Deletion is the reverse of insertion. The core idea:

  1. Locate the node containing the target key.
  2. Swap it with its inorder successor (the smallest key in the right subtree). This reduces deletion to always happening at a leaf.
  3. If the leaf is a 3-node or 4-node, simply remove the key.
  4. If the leaf is a 2-node, removing its only key would leave an empty node — which is illegal. To prevent this, transform every 2-node you encounter (on the way down) into a 3-node or 4-node first. This is the reverse of the splitting cases from insertion.

Deletion Example

We will delete 30 and then 50 from the final tree above.

Starting tree:

                         [50]
                        /    \
                     [30]    [70]
                    /    \   /   \
             [10,15,20] [40][60] [80,90,100]

Delete 30

30 is an internal node. Its inorder successor is 40 (smallest key in its right subtree). Swap 30 and 40:

                         [50]
                        /    \
                     [40]    [70]
                    /    \   /   \
             [10,15,20] [30][60] [80,90,100]

Now delete 30 from the leaf [30]. That leaf is a 2-node — but since 30 is the only key, removing it would leave an empty node.

However, looking at its sibling [10, 15, 20] (a 4-node), we can borrow from it. The sibling’s largest key (20) rotates up to the parent, and the parent’s key (40) rotates down to fill the now-empty spot:

                         [50]
                        /    \
                     [40]    [70]
                    /    \   /   \
             [10,15]  [20][60] [80,90,100]

30 is deleted. The tree remains balanced and all leaves are still at the same depth. ✓

Delete 50

50 is the root. Its inorder successor is 60 (smallest key in its right subtree). Swap 50 and 60:

                         [60]
                        /    \
                     [40]    [70]
                    /    \   /   \
             [10,15]  [20][50] [80,90,100]

Now delete 50 from the leaf [50]. It is a 2-node with no siblings to borrow from (both [20] and [60] in the right subtree are also 2-nodes).

In this case, we merge: combine the 2-node [50] with its sibling [60] (oops — actually [60] is now the root, not a sibling). Let’s be precise: the right child of the root is [70], whose left child is [50] and right child is [80,90,100]. Since [50] is a 2-node and we must delete from it, we can borrow from the rich sibling [80, 90, 100]. The sibling’s smallest key (80) rotates up to the parent [70], and 70 rotates down to fill the gap:

                         [60]
                        /    \
                     [40]    [80]
                    /    \   /   \
             [10,15] [20][70] [90,100]

50 is deleted. Final tree:

                         [60]
                        /    \
                     [40]    [80]
                    /    \   /   \
             [10,15] [20][70] [90,100]

Still height 2, all leaves at the same depth. ✓

📌 Key takeaway from deletion: The 2-3-4 tree never lets a node go empty. If you need to delete from a 2-node, you always first fatten it up — either by borrowing from a sibling or by merging with a sibling — before removing the key. This is the structural guarantee that keeps the tree balanced after every operation.

Advantages and Disadvantages of 2-3-4 Trees

Advantages: - \(O(\log n)\) height — all operations guaranteed efficient. - All leaves at the same depth — no degenerate cases. - Sorted order maintained automatically. - Generalizes easily to larger nodes (B-trees). - Suitable as a foundation for external data structures (disk-based storage).

Disadvantage: - Multiple node types (2-node, 3-node, 4-node) — implementation requires constructing and destructing different node sizes during splits and merges, which is messy in practice.

💡 The connection to B-trees: If you use a single uniform node type with space for 3 keys and 4 pointers (and allow it to be partially filled), you get a B-tree. A 2-3-4 tree is exactly a B-tree with parameter \(n = 4\). B-trees (and their variant, B+-trees) are what real database engines like PostgreSQL and MySQL actually use for their indexes.

Putting It All Together

Concept What it solves
Ordered index Enables fast lookup without scanning the whole table
Dense vs. sparse Trade-off between index size and lookup speed
Primary vs. secondary One physical order → one primary; unlimited secondaries
Multilevel index Handles indexes too large to fit in memory
BST (balanced) Optimal in-memory search: \(O(\log n)\)
2-3-4 tree Extends balanced search to external storage; precursor to B-trees

The progression is logical: plain indexing → layered indexing → tree-structured indexing → multi-key node trees → B/B+-trees (next topic).
